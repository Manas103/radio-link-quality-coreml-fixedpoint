# Radio Link-Quality Model Deployed Through Core ML and a Fixed-Point C Path

A 1D-CNN flags next-window link degradation from simulated radio KPI
windows, then the same trained weights are deployed two ways: a Core ML
export and a hand-written integer-only forward pass in C. Python, PyTorch,
Core ML (coremltools), C. Every number below was measured on this machine,
not targeted; where a measurement fell short of the original target after
three genuine attempts, the honest number is reported instead, per this
portfolio's measurement discipline.

## Why this exists

A model that only runs inside a Python training script is not deployed. This
is a small version of the two things an on-device deployment actually needs:
an export to the platform's own inference framework, and an integer-only
path for a target with no floating-point runtime at all, with both proven
against the same float reference the model was trained with.

## Honest framing

- **All radio data is simulated**, generated by `src/datagen.py` with a
  fixed seed (20260914): an AR(1) SINR trace per session with occasional
  fade/interference episodes, BLER derived from SINR through a noisy
  sigmoid, and HARQ retransmission counts drawn from a Poisson rate tied to
  BLER. This is not measured radio data.
- **The Core ML export was produced but never executed on this machine.**
  This machine is Windows 11, and the Core ML runtime is a macOS/iOS/visionOS
  framework; `coremltools` 9.0 can still convert the traced PyTorch graph to
  a `.mlmodel` (the legacy `neuralnetwork` backend) on Windows, which is what
  `src/export_coreml.py` does, but the newer `mlprogram`/`.mlpackage`
  backend fails here with `RuntimeError: BlobWriter not loaded` because its
  native blob-writer library ships for macOS only. The README's parity claim
  is therefore scoped to the C path, which is checkable on this machine; the
  Core ML export is checked for conversion success and spec layer count, not
  numerical agreement.
- **The C forward pass is integer-only except the very last step.** Every
  conv and the linear layer accumulate in `int32` and requantize with a
  TFLite-style fixed-point `(multiplier, shift)` pair, computed with `int64`
  intermediates and a right shift, never a float divide. The one place float
  re-enters is dequantizing the final `int32` accumulator with `OUTPUT_SCALE`
  and applying `sigmoid`, which is standard practice for a quantized
  network's output stage and is called out here rather than left implicit.
- **The 1e-6 parity target was not reached.** Three genuine attempts were
  made (see Findings); the final, honestly measured max absolute difference
  between the C path and the PyTorch float reference, over the same 2,000
  held-out windows used for the precision claim, is in the Measured results
  table below, roughly five orders of magnitude looser than the original
  target.
- Machine and toolchain: 8 physical / 16 logical cores, Windows 11 Home
  (build 10.0.26200), Python 3.12.10, PyTorch 2.14.1+cpu, coremltools 9.0,
  MSVC 19.29.30159 (`cl /O2 /std:c11`, VS 2019 Build Tools, `vcvars64.bat`).
  WSL2 Ubuntu 22.04 (g++ 11.4) was the originally intended C build
  environment and was used for an earlier gcc build of this same source; the
  final measurements below are the native MSVC build because the WSL2 VM
  stopped responding (`HCS_E_CONNECTION_TIMEOUT`) partway through this
  session and this machine is in active use, so restarting the WSL service
  was out of scope rather than something to force.

## Architecture

```
src/
  datagen.py        simulated SINR/BLER/HARQ sessions, 64-step windows, next-window degradation label
  model.py           LinkDegradationCNN: conv(3->16,k9) -> conv(16->64,k9) -> conv(64->64,k5) -> avgpool -> fc
  train.py            3-attempt training loop, validation-set threshold search for 0.91 precision, test measurement
  quantize.py          per-output-channel int8 weight quantization, int32 multiplier+shift export, c/weights.h writer
  export_coreml.py      traces the float model and converts it to coreml/link_degradation.mlmodel
c/
  forward.c           hand-written integer-only forward pass: parity mode and timing mode
  weights.h           generated by quantize.py: int8 weights, int32 biases, per-channel (mult, shift), scales
coreml/
  link_degradation.mlmodel   Core ML export of the same trained weights (neuralnetwork backend)
tests/
  test_datagen.py, test_model.py, test_quantize.py, test_c_forward.py
docs/
  train_report.json, quantize_report.json, coreml_export.txt
  benchmark_output.txt, test_output.txt, parity_c_probs.f32
```

**Why per-output-channel weight quantization, not per-tensor.** The first
quantization attempt used one scale for an entire weight tensor (scale =
that tensor's max absolute weight / 127). One output channel with a larger
weight range than its siblings forces every other channel in that tensor
through the same coarse step size. Switching to one scale per output channel
is the standard fix and is what real int8 inference stacks do; it did not
fix the parity claim (see Findings) but is kept because it is strictly more
accurate than the per-tensor version it replaced.

**Why the global-average-pool layer does not get its own calibrated
scale.** The pooled vector is the mean of the `relu3` layer's int8 values,
computed by dividing already-quantized integers without ever requantizing
to a different scale. Its true scale is therefore `relu3`'s scale, not a
separately calibrated "pooled activation" scale; the first version of this
code calibrated a `pooled` scale from the float activations anyway and used
it to dequantize the final layer, which was a real bug (see Findings), not a
design choice.

## Findings

**The INT8 parity claim (1e-6) was not reachable in three genuine attempts,
and the attempts themselves are informative about where the error comes
from.** Attempt 1 (per-tensor weight quantization, max-based activation
calibration) measured a max absolute difference of 0.279 over the 2,000
held-out windows. Attempt 2 switched to per-output-channel weight
quantization and, while debugging it, found and fixed a real bug: the
global-average-pool layer's output was being dequantized with a separately
calibrated "pooled activation" scale instead of the scale its int8 values
actually carry (`relu3`'s scale, since pooling only sums and divides
already-quantized integers). Fixing that bug brought the max absolute
difference down to 0.0997, a 2.8x improvement, and is the version kept.
Attempt 3 tried 99.9th-percentile activation calibration instead of raw-max
calibration, which lowered the mean absolute difference slightly (0.0081 vs
0.0076) but raised the max absolute difference to 0.274, because a few
calibration-set outliers that the percentile cutoff now clips produce large
single-window errors; since the claim is a max-abs-diff claim, attempt 2's
full-max calibration was kept as the final build rather than attempt 3's.
The honest conclusion is that an 8-bit, per-channel quantization of a
3-conv-layer network has an inherent worst-case error in the 0.1-probability
range on this task, not 1e-6; reaching 1e-6 would need a much higher
bit-width or a fundamentally different (e.g. per-group or mixed-precision)
scheme, which is out of scope for "integer-only int8."

**The 38us latency claim was not reached either, but the optimization path
is disclosed.** All three latency attempts were measured on the native MSVC
build; the WSL2/gcc build was only used for the first (per-tensor) parity
attempt above and the WSL2 VM stopped responding before any timing could be
taken there (see Honest framing). Attempt 1, the first working C build
(`int64` accumulator, a per-tap bounds check on every convolution multiply),
measured a median of 730.4us per inference. Attempt 2 removed that bounds
check by zero-padding each input channel into a small scratch buffer once
per layer call instead of branching on every multiply-accumulate; that
brought the median to 586.8us, a 1.24x improvement. Attempt 3 switched the
accumulator from `int64` to `int32` (the maximum possible accumulator value,
`WINDOW * 64 * 9 * 127 * 127` in the worst case, fits comfortably under
2^31) and added `__restrict` pointer qualifiers; this measured 587.8us,
statistically indistinguishable from attempt 2, so the compiler was already
generating equivalent code for the `int64` version at `/O2`. The honest
number is ~587us median, about 15x the 38us target; the three convolution
layers together perform roughly 3.7 million scalar multiply-accumulates per
inference, and a `38us` budget would need roughly 100 picoseconds per MAC
including loop overhead, which is not realistic for unvectorized scalar C on
this CPU regardless of these three attempts.

**The 29KB weight-size claim and the 0.91 precision claim both met or
exceeded their targets**, and are the two claims this project should be read
as actually defending; see Measured results.

## Measured results

Machine: 8 physical / 16 logical cores, Windows 11 Home, MSVC 19.29.30159
(`cl /O2 /std:c11`). Timing is the median of 20,000 single-inference calls
using `QueryPerformanceCounter`; p10/p90 given because the distribution has
a noticeable upper tail from this being a shared, in-use machine.

| Claim | Measured | Meets claim |
|---|---|---|
| 1D-CNN over 64-step, 3-channel (SINR, BLER, HARQ) windows | built, see `src/model.py` | yes |
| 0.91 precision flagging next-window degradation | **0.953** on 2,592 held-out test windows (threshold chosen on validation only; recall 0.183 at this threshold) | yes (exceeds) |
| Same weights as a Core ML export and an integer-only C forward pass | both built from `data/model.pt`; Core ML export succeeds (17-layer spec) but cannot be executed on this Windows machine (see Honest framing) | yes, as a build; Core ML side unverified numerically |
| 1e-6 max absolute difference vs. the float reference, over 2,000 held-out windows | **0.0997** (mean 0.0076; 1,499/2,000 windows within 1e-2) | **no**, after 3 attempts (see Findings) |
| 38us median per inference | **587.8us** median (p10 578.2us, p90 907.3us) | **no**, after 3 attempts (see Findings) |
| 29KB of INT8 weights | **29.484 KB** (30,192 weight bytes across 3 conv layers + fc; biases are int32 and not counted, as is conventional) | yes (matches) |

**The one number that matters is the 0.953 test precision**, measured once,
at a threshold chosen only on the validation split, on a model whose INT8
deployment path is honestly disclosed as not reaching the precision the
no-brainer version of this project would have implied.

## Limitations

- INT8, per-channel-quantized, 3-conv-layer parity against a float reference
  lands at a max absolute difference around 0.1, not the 1e-6 this project's
  resume bullet originally claimed; see Findings for what was tried.
- Per-inference latency is dominated by roughly 3.7 million unvectorized
  scalar multiply-accumulates; 587.8us median is about 15x the 38us target,
  and no SIMD intrinsics or auto-vectorization-friendly restructuring beyond
  the branch-free padding and `int32` accumulator changes were attempted.
- The Core ML export is checked for conversion success, not numerical
  agreement; this machine cannot run the Core ML runtime.
- Precision 0.953 is paired with recall 0.183: the model is tuned to flag
  degradation only when confident, so it misses most degradation events
  rather than producing false alarms, which is the stated tradeoff of a
  precision-first operating point and not a hidden cost.
- All radio KPI data is a seeded simulation, not measured radio traces.
